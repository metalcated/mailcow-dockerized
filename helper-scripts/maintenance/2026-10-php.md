# October 2026: PHP-only security update

Deployment status: prepared for staged server testing, not production-validated.
Base: `legacy` commit `925ba011`. Branch: `feature/october-2026-security-backports`.

## Scope and compatibility

- PHP moves from `ghcr.io/mailcow/phpfpm:8.2.29-2` to `8.2.35-1`, pinned to the
  corrected multi-architecture digest
  `sha256:f8fe320173eb99afeb3cfb65ecb3b45c92d7a56c9890a516efbcb13e5ca647fa`.
- `PHPFPM_IMAGE` can override the image for rollback. No local image build is needed.
- The unchanged, executable legacy PHP startup script is mounted read-only over
  `/docker-entrypoint.sh`. The new image's script otherwise introduces
  `spamalias.permanent`, which is absent from this fork's schema.
- `session.upload_progress.enabled = Off` is the only PHP configuration change.
  Ordinary uploads and the existing upload size limits remain enabled.
- No schema source/version, Dovecot authentication, Postfix, Nginx, SOGo, theme,
  routing, proxy, Autodiscover, IPv6, or firewall changes are included.

The retained startup script still performs its usual database initialization
check, event recreation, Redis/session setup, cache maintenance, and PHP hooks.
It also checks MariaDB system tables through dockerapi and can restart Postfix
if a system-table upgrade is reported. This update does not add those behaviors.
Stop before deployment if the database schema version is not `20112024_1105`,
or if unexplained pending system-table upgrades or PHP hooks are present.

Sources: [upstream PHP security update](https://github.com/mailcow/mailcow-dockerized/pull/7534),
[corrected image notice](https://github.com/mailcow/mailcow-dockerized/issues/7538).
Disabling upload-progress tracking alone is not a substitute for the patched runtime.

## Local validation

Verified on October 28, 2026 using local ARM64 Docker Desktop. The pinned PHP
binary reports 8.2.35; the offline runtime and isolated database checks pass.
No production service, database, mailbox, or Outlook client was used locally.

The focused checks compare the resolved compose configuration with the known
baseline, including an image rollback and a retry. They require every non-PHP
service and every other PHP setting/mount to remain unchanged.

Offline image checks cover the actual PHP version, extensions, FPM pool config,
startup syntax/tools, worker read permissions, first-party PHP syntax, existing
password hashing with rejection of a wrong password, and Twig output escaping.
The database fixture creates a temporary MariaDB 10.11 container with no host
ports, outbound networking, host directories, or production data. It recreates
the exact legacy events twice, checks the missing `permanent` column, and uses
PHP PDO to verify cleanup while the upstream query fails as expected.

Run the structural checks without a Docker daemon:

```sh
python3 helper-scripts/tests/test_phpfpm_legacy_update.py
```

After pulling the pinned PHP image and `mariadb:10.11` into an isolated test host:

```sh
MAILCOW_TEST_PHP_RUNTIME=1 MAILCOW_TEST_PHP_DATABASE=1 python3 helper-scripts/tests/test_phpfpm_legacy_update.py
```

Use `MAILCOW_TEST_PLATFORM=linux/amd64` for x86-64 image checks on an ARM host.
Local x86-64 emulation stalled and was stopped; it is not a passing result.
Verify the actual server binary below before restarting PHP.

These checks do not establish production database compatibility, HTTP login,
Redis session persistence, SOGo SSO, attachment handling, or Outlook behavior.
Those remain live release gates. Do not run the fixture suite on production
as part of this runbook; use the narrower checks below instead.

## 2. Preserve image rollback and check out the feature branch

Keep this shell open through deployment and rollback. The local rollback tag
preserves the exact running image even if its upstream tag has changed.

```sh
PHPFPM_CONTAINER=$(docker compose ps -q php-fpm-mailcow)
test -n "$PHPFPM_CONTAINER"
PHPFPM_ROLLBACK_ID=$(docker inspect --format '{{.Image}}' "$PHPFPM_CONTAINER")
export PHPFPM_ROLLBACK_IMAGE="mailcow-phpfpm-rollback:pre-october-2026-$(date +%Y%m%d%H%M%S)"
docker image tag "$PHPFPM_ROLLBACK_ID" "$PHPFPM_ROLLBACK_IMAGE"
printf '%s\n' "$PHPFPM_ROLLBACK_IMAGE" "$PHPFPM_ROLLBACK_ID"
git fetch origin
git switch --track origin/feature/october-2026-security-backports
git log -1 --oneline
git diff --stat legacy...HEAD
git status --short
test -x data/Dockerfiles/phpfpm/docker-entrypoint.sh
docker compose config --quiet
```

If the local feature branch already exists, use `git switch` followed by
`git pull --ff-only origin feature/october-2026-security-backports` instead.
If Git refuses due to local changes or divergence, stop. Do not reset, force,
stash secrets, or discard generated files to get past the error.

## 3. Pull and validate without starting the new PHP service

Confirm this resolves to the pinned `8.2.35-1` digest, not an environment or
compose override. Some Compose versions also list dependency images when a
service is selected, so filter the image list before checking the PHP target.
Resolve any mismatch before proceeding.

```sh
PHPFPM_TARGET=$(docker compose config --images php-fpm-mailcow | awk '/^ghcr[.]io\/mailcow\/phpfpm[:@]/')
printf '%s\n' "$PHPFPM_TARGET"
test "$PHPFPM_TARGET" = 'ghcr.io/mailcow/phpfpm:8.2.35-1@sha256:f8fe320173eb99afeb3cfb65ecb3b45c92d7a56c9890a516efbcb13e5ca647fa'
docker compose pull php-fpm-mailcow
docker run --rm --network none --entrypoint php "$PHPFPM_TARGET" -r 'echo PHP_VERSION, PHP_EOL; exit(PHP_VERSION === "8.2.35" ? 0 : 1);'
docker compose run --rm --no-deps --entrypoint bash php-fpm-mailcow -n /docker-entrypoint.sh
docker compose run --rm --no-deps --entrypoint php-fpm php-fpm-mailcow -t
docker compose run --rm --no-deps --entrypoint php php-fpm-mailcow -r 'echo "upload_progress=", var_export(ini_get("session.upload_progress.enabled"), true), PHP_EOL; exit(ini_get("session.upload_progress.enabled") ? 1 : 0);'
```

The one-off compose checks mount the normal configuration but override the
entrypoint: they do not run initialization, migrations, or PHP hooks. All must
exit successfully before the service is recreated.

## 5. Live acceptance gate

- Log in and out as administrator and as a mailbox user. Verify rejected login
  with a wrong password using a disposable test account, not repeated production
  attempts that might trigger a ban.
- Open quarantine, inspect a message, and test release using a known safe item.
- Check SOGo SSO, the existing dark theme, a message preview, and a draft attachment.
- Edit a harmless setting on a disposable mailbox, reopen it, confirm persistence,
  then restore it. If API access is configured, verify existing API permissions.
- In an already configured New Outlook account, receive and send an external
  test message; verify folder navigation, read/unread state, draft save/reopen,
  and attachment upload/download. Close and reopen Outlook to test reconnect.
- Confirm the recipient received outbound mail and that an external reply was
  actually delivered, not merely accepted into Postfix's queue.
- Recheck logs for PHP fatal errors, Redis/session failures, authentication
  errors, SQL errors, and broken internal map requests.

Adding a new New Outlook account was already failing before this update. Track
that separately; do not remove a working production account to test setup.
Routine cache clearing may require a fresh web login and is not by itself an
Outlook password failure. Stop on any new regression and roll back PHP.

## 6. Image rollback and retry

Roll back using the exact saved image, leaving the unchanged legacy startup
override and upload-progress hardening in place:

```sh
test -n "$PHPFPM_ROLLBACK_IMAGE"
docker image inspect "$PHPFPM_ROLLBACK_IMAGE" --format '{{.Id}}'
export PHPFPM_IMAGE="$PHPFPM_ROLLBACK_IMAGE"
docker compose config --images php-fpm-mailcow
docker compose up -d --no-deps --force-recreate --pull never php-fpm-mailcow
docker compose exec -T php-fpm-mailcow php -v
docker compose logs --since=5m --tail=100 php-fpm-mailcow nginx-mailcow
```

Recheck web login, SOGo, Outlook reconnect, and send/receive. If this shell is
lost, locate the saved `mailcow-phpfpm-rollback` tag in `docker image ls` before
doing anything else. A shell override does not persist across future sessions;
after a rollback, stop and coordinate a durable configuration before any later
compose operation.

For an approved retry after diagnosis:

```sh
unset PHPFPM_IMAGE
docker compose config --images php-fpm-mailcow
```

Verify the pinned target again, then repeat sections 3-5. Do not restore the
whole server snapshot for an image-only failure: it can discard newer mail.
Merge this branch into `legacy` only after the live acceptance gate passes.
